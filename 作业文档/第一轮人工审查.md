# 人工审查（重构前问题发现）

## 1. 审查范围与方法

- **审查范围**：`main.py`（CLI/交互）、`services.py`（业务）、`models.py`（领域模型）、`storage.py`（持久化）、`utils.py`（输入输出与通用函数）。
- **审查目标**：在不依赖度量工具前提下，从可读性、可修改性、可测试性三类质量属性出发，识别“AI 代码常见可维护性问题”，形成可追溯的问题清单，为后续 Pylint/Radon/CodeQL 的量化对比提供“定性基线”。
- **审查维度（建议在报告中写成小标题）**：
  - 可读性：命名、函数长度/嵌套、重复逻辑、控制流清晰度、信息密度（是否一行塞太多）。
  - 可修改性：职责边界、耦合点、规则散落、数据一致性风险、配置管理、扩展点设计。
  - 可测试性：依赖可注入性（I/O、时间、存储）、副作用隔离、可观察性（返回值/状态）、异常路径可构造性。

## 3. 本项目人工审查发现的问题（重构前）

### 3.1 分层与职责边界问题（高优先）

- **R-01：服务层方法职责过重，修改成本高**  
  - **证据**：`LibraryService.borrow_book` 同时完成用户查找、用户状态校验、图书查找、库存校验、借阅上限校验、重复借阅校验、记录创建、库存扣减、持久化保存。见 [services.py:borrow_book](file:///e:/路在何方？/软件体系结构/library_system/services.py#L262-L311)。  
  - **影响**：新增/调整任一规则都可能改动整个函数；难以针对单条规则做单元测试隔离。
  - **改进方向**：拆分为“查找”“校验”“执行”“保存”四类私有方法；将规则校验抽成可复用函数（例如 `validate_borrow_eligibility`）。

- **R-02：持久化调用散落在业务流程中，容易漏改/漏保存**  
  - **证据**：多处出现 `save_books/save_records/save_users`，例如借书保存图书与记录、还书保存图书与记录、添加/更新分别保存。见 [services.py](file:///e:/路在何方？/软件体系结构/library_system/services.py)。  
  - **影响**：后续若引入“事务式保存”“统一保存策略”“延迟写入”等，会牵动多个函数修改，回归风险高。
  - **改进方向**：统一 `save_all` 或工作单元式保存入口（至少做到“借还书流程只在一个地方保存”）。

- **R-03：CLI 逻辑过长且与业务流程耦合，扩展困难**  
  - **证据**：`LibraryCLI.book_menu/user_menu/borrow_menu` 内部同时负责展示列表、采集输入、拼装字典、调用 service、打印提示。见 [main.py:book_menu](file:///e:/路在何方？/软件体系结构/library_system/main.py#L56-L142)、[main.py:user_menu](file:///e:/路在何方？/软件体系结构/library_system/main.py#L166-L244)、[main.py:borrow_menu](file:///e:/路在何方？/软件体系结构/library_system/main.py#L245-L302)。  
  - **影响**：新增交互项或更换 UI（例如 Web/GUI）时迁移成本高；也不利于在实验二中做端到端/集成测试。
  - **改进方向**：菜单分支提取为 `_handle_xxx()` 小函数；把“输入校验”边界尽量放在输入层或统一 DTO/校验层。

### 3.2 重复代码与命名问题（中-高优先）

- **R-04：查找对象逻辑重复（Book/User/Record）**  
  - **证据**：尽管已有 `_find_book_obj/_find_user_obj/_find_record_obj`，但多个方法仍手写循环查找（例如 `borrow_book/return_book/delete_book/delete_user/update_book/update_user`）。见 [services.py](file:///e:/路在何方？/软件体系结构/library_system/services.py)。  
  - **影响**：规则调整或查找方式变化会造成多点修改；增加一致性缺陷概率。
  - **改进方向**：统一使用 `_find_xxx`；或进一步引入“找不到就返回错误”的统一辅助函数。

- **R-05：存在泛化变量命名，降低理解速度**  
  - **证据**：如 `temp/data/flag/result/info` 等，缺乏语义。典型见 [services.py:update_book](file:///e:/路在何方？/软件体系结构/library_system/services.py#L93-L140)、[services.py:delete_book](file:///e:/路在何方？/软件体系结构/library_system/services.py#L78-L91)。  
  - **影响**：阅读时需要额外推理变量角色；后续修改更容易误用变量。
  - **改进方向**：用业务语义命名（`target_book`, `isbn_conflict`, `record_to_return` 等）。

- **R-06：模型与工具函数存在“信息密度过高”的写法**  
  - **证据**：`models.py` 的 `to_dict()` 基本是一行塞完整 dict；阅读成本高。见 [models.py:Book.to_dict](file:///e:/路在何方？/软件体系结构/library_system/models.py#L22-L38)、[models.py:User.to_dict](file:///e:/路在何方？/软件体系结构/library_system/models.py#L54-L69)。  
  - **影响**：可读性下降；字段增删时 diff 不友好、容易遗漏。
  - **改进方向**：格式化为多行键值，或统一序列化工具（保持简单即可）。

### 3.3 规则与一致性/边界处理问题（中-高优先）

- **R-07：规则配置缺少持久化与统一管理**  
  - **证据**：`default_borrow_days` 仅保存在内存，重启恢复为 30。见 [services.py:__init__](file:///e:/路在何方？/软件体系结构/library_system/services.py#L12-L17)、[services.py:set_default_borrow_days](file:///e:/路在何方？/软件体系结构/library_system/services.py#L375-L380)。  
  - **影响**：规则不可追溯；后续扩展“不同用户类型不同借阅规则”修改范围大。
  - **改进方向**：引入配置存储（哪怕是单独 JSON）或写入 records/users 的 meta 区域（保持实验规模即可）。

- **R-08：部分字段类型转换分散，输入边界不稳定**  
  - **证据**：CLI 中收集到的 `publish_year/total_count/available_count` 有时以字符串形式传入 service，service 再转 int；有的字段在 CLI 中先转。见 [main.py:book_menu update](file:///e:/路在何方？/软件体系结构/library_system/main.py#L95-L130)、[services.py:update_book](file:///e:/路在何方？/软件体系结构/library_system/services.py#L120-L137)。  
  - **影响**：同一字段在不同路径表现不一致；实验二写测试时要覆盖更多输入变体。
  - **改进方向**：统一“输入层负责转型/校验”或“服务层负责转型/校验”的边界（二选一并保持一致）。

- **R-09：异常体系不清晰，不利于测试异常路径**  
  - **证据**：主要以 `(bool, str)` 返回错误信息，而不是异常类型或错误码。全局存在于 [services.py](file:///e:/路在何方？/软件体系结构/library_system/services.py)。  
  - **影响**：测试只能断言字符串；后续增加国际化/错误码/日志会引发广泛修改。
  - **改进方向**：实验一可以先不强推异常体系；但实验二至少应把“可断言的错误类型/错误码”纳入设计（例如定义 `Enum` 或简单错误码）。

### 3.4 可测试性专项问题（为实验二铺垫）

- **R-10：时间依赖不可控，逾期相关测试构造困难**  
  - **证据**：逾期计算依赖 `datetime.now()`，如 [models.py:calculate_overdue_days](file:///e:/路在何方？/软件体系结构/library_system/models.py#L122-L135)、[utils.py:now_date_text](file:///e:/路在何方？/软件体系结构/library_system/utils.py#L27-L36)。  
  - **影响**：测试不稳定；难以构造特定日期边界。
  - **改进方向**：注入“当前日期提供者”（函数参数或依赖注入），或在测试中显式传 `now_text`（当前已有部分参数支持）。

- **R-11：业务方法中包含写文件副作用，单测会污染真实数据**  
  - **证据**：`JsonStorage` 默认读写项目目录 JSON。见 [storage.py:JsonStorage.__init__](file:///e:/路在何方？/软件体系结构/library_system/storage.py#L7-L15)。  
  - **影响**：单测需要隔离环境，否则会破坏 `books.json/users.json/records.json`。
  - **改进方向**：实验二编写 `FakeStorage` 或使用临时目录注入 `JsonStorage(base_dir=tempdir)`。
