# 五．代码

## 5.1 实现语言与关键技术

本项目继续采用 Python 作为实现语言，整体保持命令行图书馆管理系统的基本形态。实验一中，主要通过函数拆分、辅助方法抽取、统一菜单分发和命名优化等方式提升系统的可读性与可修改性；实验二中，则围绕可测试性继续改造，在不改变核心业务语义的前提下，引入 `pytest` 自动化测试、`coverage` 覆盖率统计以及基于临时目录的测试隔离机制。

本次实验涉及的关键技术主要包括以下几个方面：

- 结构重构技术：公共辅助方法提取、流程分阶段拆分、统一菜单分发、文档字符串补充。
- 自动化测试技术：`pytest`、`coverage`、`tmp_path`、`monkeypatch`、`capsys`。
- 持久化隔离技术：`JsonStorage(base_dir=tmp_path)`。
- 质量度量技术：`Pylint`、`Radon`、`CodeQL`、`Coverage`。

这些技术共同支撑了系统从“可运行但难维护、难验证”的初始状态，逐步演化为“结构更清晰、可维护性更高、具备自动回归能力”的实验结果。

## 5.2 关键代码清单

### 5.2.1 实验一：借书流程从集中式校验改为分阶段校验

该代码体现了实验一中最重要的结构改进之一，即把原本堆叠在 `borrow_book()` 中的大量职责拆分为对象获取、规则校验、记录创建和统一保存几个阶段。

```python
def borrow_book(self, user_id: str, book_id: str, note: str = "") -> tuple[bool, str]:
    user = self._find_user_obj(user_id)
    if user is None:
        return False, "用户不存在。"
    book = self._find_book_obj(book_id)
    if book is None:
        return False, "图书不存在。"
    is_valid, message = self._validate_borrow_request(user, book)
    if not is_valid:
        return False, message
    record, due_date = self._create_borrow_record(user, book, note)
    book.available_count -= 1
    self.records.append(record)
    self._save_books_and_records()
    return True, f"借书成功，应还日期为 {due_date}。"
```

代码说明：重构前的借书流程同时承担对象查找、状态校验、库存判断、借阅上限校验、重复借阅检查、记录创建和持久化保存，职责过于集中。重构后公开方法只保留业务骨架，把规则检查下沉到 `_validate_borrow_request()`，把记录构造下沉到 `_create_borrow_record()`，再通过 `_save_books_and_records()` 统一收敛保存逻辑。这样主流程更接近业务语义，也使后续规则扩展和测试切入点更加清晰。

### 5.2.2 实验一：菜单控制从 if/elif 链改为统一菜单分发

该代码体现了实验一中 CLI 层的重要改进，即将菜单层从“长分支链”演化为“统一分发器 + 处理器映射”的结构。

```python
self._run_menu_loop(
    "图书管理",
    ["添加图书", "删除图书", "修改图书信息", "查询图书", "显示全部图书", "返回主菜单"],
    {
        "1": self._handle_add_book,
        "2": self._handle_delete_book,
        "3": self._handle_update_book,
        "4": self.search_books_menu,
        "5": self._handle_show_books,
    },
    "6",
)
```

代码说明：重构前的 `book_menu()`、`user_menu()`、`borrow_menu()` 都采用重复的 `if/elif` 链进行分支控制，一个函数同时承担菜单展示、输入读取、分支判断和处理器调用，导致复杂度高、重复率高。重构后通过 `_run_menu_loop()` 抽出公共流程，子菜单只保留菜单项配置和处理器映射。这样不仅减少了分支数量，也让 `main.py` 的职责边界更清晰，是本次实验一复杂度下降最明显的改进之一。

### 5.2.3 实验一：图书更新逻辑从内联分支改为辅助方法承载复杂字段处理

该代码体现了实验一对高复杂度核心函数的拆分策略。

```python
def update_book(self, book_id: str, info: dict[str, Any]) -> tuple[bool, str]:
    book_to_update, error_message = self._get_book_or_error(book_id)
    if error_message:
        return False, error_message
    assert book_to_update is not None
    is_updated, message = self._apply_book_updates(book_to_update, info)
    if not is_updated:
        return False, message
    self._save_books()
    return True, "图书信息修改成功。"
```

代码说明：重构前的 `update_book()` 同时负责图书查找、字段解析、ISBN 唯一性校验、库存修正和保存，属于典型的大函数。重构后公开方法只保留获取对象、调用更新、统一保存三个步骤，而复杂字段更新由 `_apply_book_updates()` 集中处理。这样虽然辅助函数内部仍然存在一定分支，但复杂度被封装到了更适合的局部位置，公开接口更加短小清晰，更利于阅读和后续维护。

### 5.2.4 实验二：测试夹具与临时目录隔离

该代码体现了实验二中最核心的可测试性改进，即通过临时目录和依赖注入，使测试过程不影响项目真实数据。

```python
@pytest.fixture
def storage(tmp_path):
    """提供隔离的 JSON 存储目录。"""
    return JsonStorage(base_dir=tmp_path)


@pytest.fixture
def service(storage):
    """提供基于临时目录的业务服务对象。"""
    return LibraryService(storage=storage)
```

代码说明：`tmp_path` 是 `pytest` 提供的临时目录夹具，每次执行测试时都会生成独立目录，因此不会污染项目根目录下真实的 `books.json`、`users.json`、`records.json`。`JsonStorage(base_dir=tmp_path)` 将存储层重定向到临时路径，体现了“通过依赖注入隔离外部环境”的测试思想。`service(storage)` 则进一步将测试对象统一封装为 `LibraryService`，使每个测试函数都可以直接获得一个干净、可重复使用的业务服务实例。这种做法是实验二可测试性改造的基础。

### 5.2.5 实验二：借书主流程测试

该代码对应系统最核心的业务路径之一，用于验证借书成功后库存变化、借阅记录生成和备注写入是否全部正确。

```python
def test_borrow_book_creates_record_and_reduces_stock(service):
    """借书成功后应生成记录并减少库存。"""
    assert add_book(service)[0] is True
    assert add_user(service)[0] is True

    ok, message = service.borrow_book("U-1001", "B-1001", note="单元测试借阅")

    assert ok is True
    assert "借书成功" in message
    assert service.books[0].available_count == 4
    assert len(service.records) == 1
    assert service.records[0].note == "单元测试借阅"
```

代码说明：在执行借书前，测试先通过辅助函数构造图书和用户数据，保证测试前置条件清晰明确。之后调用 `service.borrow_book()`，并从返回结果、库存变化、记录生成、备注写入等多个角度进行断言。这里不是只验证“返回成功”，而是同时验证借书流程产生的关键业务副作用是否全部正确。这类测试能够较好体现“围绕核心业务路径构造断言”的测试思路，也是实验二自动回归验证的重点之一。

### 5.2.6 实验二：库存不足边界测试

该代码体现了实验二对边界条件的关注，也是本次测试中最能说明“测试驱动发现缺陷”的一个例子。

```python
def test_borrow_book_rejects_out_of_stock_book(service):
    """库存不足时不能借书。"""
    assert add_book(service, total_count=1, available_count=0)[0] is True
    assert add_user(service)[0] is True

    ok, message = service.borrow_book("U-1001", "B-1001")

    assert ok is False
    assert message == "图书库存不足。"
    assert len(service.records) == 0
```

代码说明：该测试验证当图书库存为 `0` 时，系统是否能够正确拒绝借书请求。实际编写过程中，这个测试在首次运行时暴露出一个真实缺陷：系统在 `add_book()` 中对 `available_count=0` 的处理存在边界问题，导致 `0` 会被错误当成“未提供值”。在修复服务层逻辑后，该测试才最终通过。由此可见，自动化测试不仅能够验证代码正确性，也能够帮助发现 AI 生成代码在边界路径上的潜在问题。

### 5.2.7 实验二：工具层函数测试

除服务层外，本次实验还对工具层函数进行了自动化测试，以进一步提升系统整体可测试性。

```python
def test_input_int_handles_invalid_and_minimum(monkeypatch, capsys):
    """input_int 应处理非法输入和最小值限制。"""
    answers = iter(["abc", "0", "3"])
    monkeypatch.setattr("builtins.input", lambda _: next(answers))

    result = input_int("请输入整数：", minimum=1)

    captured = capsys.readouterr()
    assert result == 3
    assert "请输入整数" in captured.out
    assert "不能小于 1" in captured.out
```

代码说明：这段代码展示了如何使用 `monkeypatch` 和 `capsys` 对交互型工具函数进行测试。`monkeypatch` 用来模拟用户输入，`capsys` 用来捕获输出内容。通过这种方式，即使是原本依赖控制台输入输出的工具函数，也可以被稳定地纳入自动化测试范围。正因如此，本轮实验二在补充工具层测试后，`utils.py` 的覆盖率提升到了 `100%`。
