# Coverage覆盖率分析

## 1. 测试执行方式

本次覆盖率统计使用 `coverage` 工具对 `pytest` 测试执行过程进行记录，执行流程如下：

```powershell
python -m coverage erase
python -m coverage run -m pytest -q
python -m coverage report -m
python -m coverage html -d .\作业文档\重构\coverage_html
```

本次测试运行结果为：

- 共执行测试用例：`33`
- 测试通过情况：`33 passed`

## 2. 覆盖率结果概览

根据 `coverage report -m` 输出结果，当前项目覆盖率如下：

| 文件                       |     语句数 | 未覆盖语句数 |     覆盖率 |

## 3. 结果分析

### 3.1 总覆盖率分析

- 当前项目总覆盖率为 `95%`，说明本次实验二已经不仅建立了基础自动化测试体系，而且对核心逻辑形成了较高强度的回归验证能力。
- 与前一轮覆盖率相比，本次结果提升明显，说明“围绕核心业务路径和低覆盖辅助模块进行定向补测”的策略是有效的。

### 3.2 services.py 覆盖率分析

- `services.py` 的覆盖率提升到 `90%`，已经从“部分覆盖”提升为“高覆盖核心业务模块”。
- 本轮新增测试重点覆盖了以下之前缺失的路径：
  - 图书与用户的查询逻辑
  - 图书和用户的更新、删除逻辑
  - 借阅记录查询与导出逻辑
  - 统计信息计算逻辑
  - 样例数据导入逻辑
- 当前未覆盖部分主要集中在少量失败分支和个别防御性路径，但已经不影响实验二“关键业务具备自动回归能力”的结论。

### 3.3 models.py 覆盖率分析

- `models.py` 的覆盖率为 `97%`，说明模型层纯逻辑测试已经比较充分。
- 当前已经覆盖了：
  - `calculate_overdue_days()`
  - `is_overdue()`
- 本轮补充后，`to_dict()` / `from_dict()`、`short_text()`、逾期判断与逾期天数计算都已基本覆盖。
- 这说明模型层天然适合做单元测试，因为依赖少、逻辑清晰、输入输出边界明确。

### 3.4 storage.py 覆盖率分析

- `storage.py` 的覆盖率为 `94%`，属于当前覆盖情况最好的业务支撑模块之一。
- 这表明使用 `tmp_path` + `JsonStorage(base_dir=tmp_path)` 的测试策略是有效的。
- 测试不仅验证了服务层逻辑，也间接覆盖了绝大部分 JSON 持久化读写路径。

### 3.5 utils.py 覆盖率分析

- `utils.py` 的覆盖率已经提升到 `100%`，是本轮定向优化中提升最明显的文件。
- 之所以能显著提升，是因为本轮专门补充了以下测试：
  - 输入函数的重试、默认值和最小值路径
  - 日期计算与字符串处理路径
  - 表格展示、菜单输出和确认输入路径
- 这说明即使是工具层函数，只要具备明确输入输出，也完全可以通过 `monkeypatch`、`capsys` 等手段进行稳定测试。

## 4. 本次覆盖率结果说明了什么

- 从“原始项目没有自动化测试”到“当前总覆盖率达到 95%”，说明系统已经具备较强的自动回归能力。
- 服务层、模型层、工具层和存储层都已获得较高覆盖，说明本次实验二并非只验证少量 happy path，而是已经覆盖了较多关键边界路径与辅助逻辑。
- 本轮覆盖率提升最明显的部分来自 `services.py` 和 `utils.py`，这表明定向补测高价值未覆盖模块是有效策略。

## 5. 可直接写进实验报告的总结

本次实验使用 `coverage` 对 `pytest` 自动化测试执行情况进行了统计。结果显示，当前项目总覆盖率达到 `95%`。其中，`services.py` 覆盖率为 `90%`，`models.py` 覆盖率为 `97%`，`storage.py` 覆盖率为 `94%`，`utils.py` 覆盖率达到 `100%`。这表明本次实验二已经能够对借书、还书、逾期判断、图书与用户更新、查询统计以及工具层关键逻辑形成较完整的自动化验证。总体来看，覆盖率结果说明系统已经从“依赖手工验证”转变为“具备高覆盖自动回归能力”，可测试性得到显著提升。
