# 工具度量与结果分析

## 一．度量目的与分析思路

为了保证本次实验的重构工作不是凭经验随意修改，而是建立在明确证据基础上的结构优化，本实验在人工审查之后，进一步引入 `Pylint`、`Radon` 和 `CodeQL` 对图书馆管理系统进行重构前基线度量。  
这些工具分别从代码规范、结构复杂度、可维护性以及自动化静态安全分析等不同角度对系统进行检查，从而形成“人工审查 + 工具度量”的分析闭环。

本阶段分析的目标主要包括：

- 从工具层面验证人工审查中发现的问题是否具有普遍性和代表性
- 明确重构前的质量基线，为后续重构后结果对比提供依据
- 找出需要优先改进的模块和函数，避免平均用力
- 通过自动化分析手段提升实验结论的客观性和可复现性

## 二．人工审查结果概述

在工具度量之前，首先对系统进行了人工审查。审查结果表明，当前项目虽然已经具备可运行的基本功能，但在结构设计和代码质量方面存在较明显的问题，主要包括：

- `main.py` 中菜单函数偏长，输入采集、流程控制、结果输出混杂在一起
- `services.py` 中多个方法同时承担查找、校验、业务处理和持久化保存职责
- 图书、用户、借阅记录的查找与校验逻辑存在重复
- 命名中出现 `data`、`temp`、`flag`、`result` 等泛化变量名
- 关键业务函数边界条件较多，但结构拆分不充分
- 当前项目缺少测试代码，不利于后续回归验证

从人工审查角度看，项目的主要问题集中在**可读性不足、可修改性较弱和可测试性支持不够**三个方面。  
这一结论为后续工具度量提供了方向，即重点观察业务层和交互层是否在复杂度、可维护性和代码规范方面存在明显薄弱区域。

## 三．Pylint度量结果分析

### 1. 总体结果

根据 `Pylint` 的重构前分析结果，当前项目总体评分为：

```text
8.65 / 10
```

这一分数说明项目基础质量并不差，代码可以运行，结构也并非完全混乱，但仍存在较多值得改进的规范性和可维护性问题。

### 2. 主要问题表现

`Pylint` 反映出的主要问题包括：

- 大量模块、类、函数缺少文档字符串
- `main.py` 中部分菜单函数局部变量过多、分支过多、语句过多
- `services.py` 中多个方法存在职责集中、分支较多的问题
- `models.py` 与 `utils.py` 存在较多超长行
- `main.py` 中出现少量未使用变量

### 3. 结果解读

`Pylint` 的结果说明，当前代码的主要问题不是语法错误，而是**结构和表达质量问题**。  
这些问题会直接影响阅读效率和修改效率，例如：

- 缺少文档字符串会降低代码自说明能力
- 函数过长会提高理解成本和改动风险
- 超长行会降低可读性和差异比较的便利性
- 未使用变量反映出接口使用不够统一

因此，`Pylint` 结果从规范与结构表达层面验证了前期人工审查的判断，即当前项目仍有较明显的可读性和可修改性优化空间。

## 四．Radon度量结果分析

### 1. 圈复杂度结果

Radon 对全项目共分析了 `85` 个代码块，平均复杂度为：

```text
Average complexity: A (4.447058823529412)
```

从平均值看，项目整体复杂度处于可接受范围，但进一步查看具体函数可以发现，复杂度热点高度集中在少数核心函数。

#### 复杂度较高的函数

交互层：

- `LibraryCLI.book_menu()`：`D (21)`
- `LibraryCLI.user_menu()`：`C (18)`
- `LibraryCLI.borrow_menu()`：`B (10)`

业务层：

- `LibraryService.update_book()`：`D (26)`
- `LibraryService.update_user()`：`C (18)`
- `LibraryService.borrow_book()`：`C (17)`
- `LibraryService.search_books()`：`C (13)`
- `LibraryService.add_book()`：`C (12)`
- `LibraryService.return_book()`：`B (10)`

这些结果表明：

- 交互层中的菜单处理逻辑存在明显堆叠
- 业务层中的核心方法承担了过多条件判断和规则处理
- 当前系统并不是“所有地方都复杂”，而是“关键热点函数明显偏重”

### 2. 可维护性指数结果

各文件的可维护性指数如下：

- `main.py - B (16.59)`
- `models.py - A (35.35)`
- `sample_data.py - A (71.56)`
- `services.py - C (0.00)`
- `storage.py - A (48.16)`
- `utils.py - A (39.88)`

其中最需要关注的是：

- `services.py - C (0.00)`

这一结果表明 `services.py` 是当前项目中最不利于后续维护和演化的模块。结合复杂度分析可以看出，其问题主要来自：

- 多个公共方法职责集中
- 业务规则与数据保存耦合较紧
- 更新、借阅和查询逻辑包含较多条件分支

相比之下，`models.py`、`storage.py`、`utils.py` 的可维护性等级均为 `A`，说明问题并不是普遍分布在所有文件中，而是集中在交互层和业务层。

### 3. 原始代码统计结果

Radon 原始统计显示：

- `LOC: 1144`
- `LLOC: 871`
- `SLOC: 1034`
- `Blank: 110`
- `Comments: 0`
- `Comment Stats: 0%`

从文件分布上看，代码主要集中在：

- `services.py`：`LOC 481`
- `main.py`：`LOC 361`

这说明当前系统的大部分复杂性都集中在这两个文件中。  
此外，项目整体注释率为 `0%`，也进一步说明当前代码虽然可运行，但在自说明能力和可读性增强方面存在明显不足。

### 4. 结果解读

`Radon` 的结果非常清楚地揭示了本项目的结构性问题：

- 平均复杂度并不高，但热点函数明显过重
- `services.py` 是当前重构的首要目标
- `main.py` 的菜单处理函数也需要拆分
- 注释和说明性信息几乎缺失，不利于长期维护

因此，从复杂度和可维护性角度看，实验一将重构重点放在 `main.py` 与 `services.py` 是合理且必要的。

## 五．CodeQL度量结果分析

### 1. 运行结果

在重构前基线阶段，项目通过 GitHub Actions 成功运行了 `CodeQL` 工作流，并在 GitHub 的 `Security and quality -> Code scanning` 页面展示了最终结果。  
本次扫描结果为：

```text
0 alerts
```

### 2. 结果解释

`0 alerts` 并不表示 `CodeQL` 没有执行，而是表示：

> CodeQL 已经成功完成扫描，但在当前查询规则下，没有发现需要在 `Code scanning` 页面报告的静态安全告警。

这一结果对本项目而言是合理的，原因主要有以下几点：

- 项目是本地命令行系统，外部攻击面较小
- 使用 JSON 文件持久化，没有复杂的数据库和网络交互
- 当前主要问题集中在结构质量，而不是典型安全漏洞
- `CodeQL` 关注的是安全风险和特定缺陷模式，不会像 `Pylint` 和 `Radon` 一样直接报告函数过长、复杂度高、注释缺失等问题

### 3. 结果意义

尽管 `CodeQL` 的扫描结果为 `0 alerts`，但这一结果依然具有明确价值：

- 证明项目已经成功接入自动化静态分析流程
- 说明工作流和 `Code scanning` 页面均正常工作
- 表明当前项目的核心短板并不是安全告警，而是维护质量问题
- 可作为后续重构后的再次扫描对照基线

因此，`CodeQL` 的结果与本次实验聚焦可读性、可修改性和可测试性的目标并不冲突，反而帮助进一步明确了实验重点。

## 六．综合分析与问题定位

将人工审查与三类工具结果综合起来，可以得到较一致的判断：

### 1. 系统问题并非平均分布，而是热点集中

主要问题集中在两个文件：

- `main.py`
- `services.py`

这两个文件同时在人工审查、Pylint 和 Radon 中表现出明显问题，说明它们是当前系统中最需要优先重构的区域。

### 2. 当前主要矛盾是“结构质量不足”

当前系统的主要问题包括：

- 菜单函数过长
- 业务方法职责过重
- 重复校验逻辑较多
- 注释和文档说明不足
- 可测试性基础薄弱

这些问题共同影响可读性、可修改性和可测试性，是实验一和实验二的主要切入点。

### 3. 当前主要矛盾不是“安全漏洞”

CodeQL 没有报出告警，这说明当前项目在默认查询规则下未表现出明显的静态安全问题。  
因此，本次实验后续的重点不应放在安全修复，而应放在：

- 模块职责梳理
- 长函数拆分
- 规则抽取与逻辑解耦
- 自动化测试补充

## 七．对后续重构的指导意义

根据当前基线结果，后续重构应按以下优先级推进：

### 1. 优先优化 `services.py`

重点方法包括：

- `update_book()`
- `update_user()`
- `borrow_book()`
- `return_book()`

目标是降低复杂度、减少分支数量、增强职责清晰度。

### 2. 拆分 `main.py` 中的长菜单函数

重点包括：

- `book_menu()`
- `user_menu()`
- `borrow_menu()`

目标是将输入采集、业务调用和结果输出进一步解耦。

### 3. 补充说明性文字与文档字符串

不要求为每一行代码添加注释，但应为：

- 模块职责
- 核心类
- 关键业务方法

补充必要说明，提升代码自说明能力。

### 4. 为实验二的可测试性改进做准备

当前基线已经说明项目结构性问题较明显，因此在完成实验一的重构后，应进一步补充自动化测试，重点覆盖：

- 借书
- 还书
- 逾期判断
- 边界条件和异常路径

## 八．本阶段结论

综合人工审查、Pylint、Radon 与 CodeQL 的结果可以得出结论：

- 当前项目具备可运行基础，但在结构设计和可维护性方面存在较明显不足
- 主要问题集中在交互层和业务层，而不是数据模型层和存储层
- `main.py` 和 `services.py` 是后续重构的重点模块
- 当前项目的主要问题属于可读性、可修改性和可测试性问题，而非典型安全漏洞问题
- 基线度量结果已经为后续“重构前后对比”提供了较清晰、较完整的证据基础
