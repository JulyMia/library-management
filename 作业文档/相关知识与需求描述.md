# 相关知识与需求描述

## 一．相关知识

### 1. 理论概念说明

本次实验围绕软件体系结构中的质量属性展开，重点关注**可读性、可修改性与可测试性**。结合本项目的实验安排，实验一主要聚焦可读性与可修改性，实验二主要聚焦可测试性。

#### （1）可读性

可读性是指代码、模块和系统结构被开发者理解的难易程度。可读性不仅体现在命名是否清晰、注释是否必要、格式是否统一，还体现在控制流程是否直观、模块划分是否合理。  
在软件开发实践中，可读性越高，开发者理解系统行为和定位问题的成本越低，团队协作效率也越高。

对于本项目而言，可读性主要体现在以下方面：

- 模块命名是否准确反映职责
- 菜单函数和业务函数是否过长
- 控制分支和条件判断是否过多
- 数据结构和输出逻辑是否易于阅读

#### （2）可修改性

可修改性是指软件在需求变化、功能扩展、错误修复或结构调整时，能够以较低成本完成修改且不引发大面积连锁影响的能力。  
从软件架构角度看，可修改性与模块间耦合程度、职责边界清晰度、规则分布方式和扩展点设计密切相关。

在本项目中，可修改性主要表现为：

- 是否能方便地调整借阅规则
- 是否能方便地新增字段、菜单项或统计功能
- 是否能在不影响其他模块的情况下局部修改业务逻辑
- 是否存在大量重复校验逻辑导致“一处修改、多处联动”

#### （3）可测试性

可测试性是指软件是否便于设计测试用例、构造输入数据、观察执行结果并验证行为正确性。  
良好的可测试性通常依赖于较清晰的分层结构、较少的隐藏副作用、明确的输入输出边界以及可注入、可替换的外部依赖。

对于本项目而言，可测试性主要体现在：

- 核心业务逻辑是否能脱离命令行界面单独测试
- 持久化、时间获取等依赖是否易于隔离
- 借书、还书、逾期判断等规则是否方便覆盖边界情况
- 测试是否能够支持后续重构后的回归验证

#### （4）AI 时代代码与质量属性的关系

本实验对象是一个具有明显 AI 辅助生成特征的图书馆管理系统。AI 生成代码通常具有“可以快速产出可运行版本”的优点，但也容易带来以下问题：

- 命名较泛化，例如 `data`、`temp`、`flag` 等变量过多
- 多个职责混在一个函数中，缺少清晰抽象
- 对异常路径和边界条件考虑不足
- 重复代码较多，逻辑集中但不易扩展
- 在 happy path 下可以工作，但在复杂维护场景下修改成本较高

这些问题会直接影响代码的可读性、可修改性和可测试性。  
因此，在 AI 时代，“代码能运行”并不等于“代码可维护”，开发者仍需要从架构和质量属性角度对 AI 生成代码进行人工审查、重构和验证。

#### （5）ICONIX 过程思想的简要引入

ICONIX 过程强调从需求出发，通过用例、领域对象和设计类之间的映射关系，逐步推进到实现阶段。它的核心价值在于：系统中的类、方法和交互流程应当能够追溯回实际需求，而不是仅凭实现便利进行堆叠式编码。

在本次实验中，ICONIX 思想的作用主要体现在以下方面：

- 从“图书管理、用户管理、借书、还书、逾期查询”等用例出发分析当前代码结构
- 检查 `main.py`、`services.py`、`storage.py` 等模块是否与需求职责相匹配
- 在重构时确保关键方法的调整不是任意拆分，而是围绕具体业务行为进行优化

也就是说，本次实验中的结构改进并不是单纯为了让代码更“漂亮”，而是为了让系统结构更符合真实业务需求，更易于理解、修改和测试。

### 2. 本次实验关注的关键技术或工具

结合当前项目和实验要求，本次实验主要使用以下工具：

#### （1）Pylint

`Pylint` 是 Python 生态中常用的静态分析工具，可以对代码风格、命名规范、函数规模、潜在坏味道等进行检查。  
本实验中使用 `Pylint` 的原因是：

- 能较直观反映模块、类、函数的可读性问题
- 能发现函数分支过多、语句过多、变量过多等结构问题
- 适合为实验一中的可读性与可修改性分析提供量化依据

#### （2）Radon

`Radon` 是 Python 代码度量工具，主要用于分析圈复杂度、可维护性指数和原始代码统计。  
本实验中使用 `Radon` 的原因是：

- 可以量化函数复杂度，识别重构重点区域
- 可以通过可维护性指数反映代码整体可维护水平
- 能为重构前后形成明确的数据对比

本实验重点关注：

- 圈复杂度（Cyclomatic Complexity）
- 可维护性指数（Maintainability Index）
- 原始统计（代码行数、注释比例等）

#### （3）CodeQL

`CodeQL` 是 GitHub 提供的代码静态分析与安全分析工具。它通过将代码抽象为数据库进行查询，从而识别潜在缺陷、危险模式和安全问题。  
本实验中选择 `CodeQL` 的原因有两点：

- 指导书明确要求必须使用 GitHub CodeQL
- 可以将分析过程接入 GitHub Actions，形成自动化质量门禁

虽然本项目规模不大，但使用 `CodeQL` 仍然具有实验意义，因为它体现了软件工程中“自动化质量检查”的工程实践思想。

#### （4）Pytest

`Pytest` 是 Python 常用的自动化测试框架，支持单元测试、参数化测试和较灵活的断言写法。  
在实验二中，`Pytest` 将作为可测试性改进的重要工具，用于：

- 为 `LibraryService` 的核心业务逻辑编写单元测试
- 覆盖正常路径与边界路径
- 支撑重构后的回归验证

#### （5）Coverage / pytest-cov

覆盖率工具用于统计测试执行过程中被覆盖到的代码比例，包括行覆盖率、分支覆盖率等。  
在实验二中，覆盖率工具的作用是：

- 量化测试改进效果
- 支撑“可测试性提升”的结果分析
- 帮助识别尚未被测试覆盖的关键路径

### 3. 技术选型理由总结

本次实验选择 `Pylint`、`Radon`、`CodeQL`、`Pytest` 和覆盖率工具，主要基于以下考虑：

- 与 Python 项目技术栈匹配，安装与执行成本较低
- 既能进行静态结构分析，也能进行测试验证
- 既能支撑实验一的可读性、可修改性分析，也能支撑实验二的可测试性分析
- 能够形成“人工审查 -> 工具度量 -> 重构优化 -> 再次度量”的完整实验闭环

## 二．需求描述

### 1. 功能性需求

本项目为命令行版图书馆管理系统，主要功能包括以下几个方面：

#### （1）图书管理

- 添加图书
- 删除图书
- 修改图书信息
- 查询图书
- 显示全部图书

#### （2）用户管理

- 添加用户
- 删除用户
- 修改用户信息
- 查询用户
- 显示全部用户

#### （3）借阅管理

- 用户借书
- 用户还书
- 查询某个用户的借阅记录
- 查询所有未归还记录
- 设置默认借阅天数

#### （4）逾期与统计功能

- 查看当前逾期记录
- 查看逾期说明
- 查看系统统计信息
- 导入样例数据

这些功能构成了本系统的基本业务范围，也是后续进行结构审查、重构和测试设计的需求基础。

### 2. 非功能性需求

本实验的非功能性需求以**可读性、可修改性和可测试性**为核心，具体说明如下。

#### （1）可读性目标

系统应具备较好的结构清晰度，使开发者能够快速理解主要模块职责和关键业务流程。具体要求包括：

- 模块边界清晰，`main.py`、`services.py`、`models.py`、`storage.py`、`utils.py` 的职责应易于区分
- 核心函数长度和分支数量应控制在合理范围内
- 命名应尽量避免过于宽泛的变量名和函数名
- 长行、重复表达和过度紧凑的代码应尽量减少

#### （2）可修改性目标

系统应具备一定的低成本演化能力，支持后续业务规则调整和功能扩展。具体要求包括：

- 借阅规则、库存更新、用户校验等逻辑应避免过度分散
- 核心业务流程应减少重复代码
- 单个函数职责应尽量单一，避免“查找 + 校验 + 更新 + 保存”全部耦合在一起
- 在新增功能或修改业务规则时，修改范围应尽量局限于少数模块

#### （3）可测试性目标

系统应便于对关键业务逻辑进行自动化测试。具体要求包括：

- 借书、还书、逾期判断等核心规则应能够编写单元测试
- 测试应能够覆盖正常路径和典型异常路径
- 持久化、日期处理等外部依赖应尽可能便于隔离
- 重构后系统应具备基本的自动化回归验证能力

#### （4）可量化目标

为了使实验结果更明确，本次实验可设置以下量化目标：

- `Pylint` 总体评分较重构前有所提升
- `Radon` 中核心函数的圈复杂度有所下降
- 可维护性指数保持在较高等级，或较重构前进一步改善
- 实验二中为核心业务模块补充自动化测试，并统计覆盖率结果

### 3. 非功能性需求的重要性

本项目虽然是一个命令行程序，但其业务流程较完整，包含图书管理、用户管理、借阅归还和逾期处理等多个功能点。  
如果只关注“功能是否能运行”，而忽视代码质量，那么随着功能增加，系统会逐渐变得难以维护、难以扩展、难以测试。

因此，本次实验中强调的非功能性需求具有以下重要意义：

- 可读性决定开发者是否能快速理解系统结构
- 可修改性决定系统能否在需求变化时稳定演化
- 可测试性决定系统是否具备持续验证和回归控制能力

这三者共同支撑软件架构质量，也是 AI 时代尤其需要关注的方面。

### 4. 为什么在 AI 时代要格外关注这些需求

AI 辅助编程显著提高了代码生成速度，但也使开发者更容易获得“能运行的初始版本”。  
然而，AI 生成代码往往倾向于优先满足功能完成，而不是优先满足结构质量，因此可能出现：

- 逻辑集中但抽象不足
- 结构可运行但难以扩展
- 异常路径和边界情况考虑不充分
- 测试支持不足，修改后难以验证正确性

因此，在 AI 时代，开发者的核心价值不只是“写代码”，更包括：

- 审查 AI 生成代码的结构合理性
- 从质量属性角度识别潜在风险
- 对代码进行重构、验证和持续改进

本次实验正是围绕这一目标展开，即通过人工审查、工具分析和结构优化，提高系统的可读性、可修改性和可测试性。
